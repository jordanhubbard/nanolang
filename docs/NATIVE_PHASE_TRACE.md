# My native publisher phase measurements

I enable `NANOLANG_NATIVE_PHASE_TRACE=1` in my fresh-route audit to observe the Stage 1 and Stage 2 native CLI helper builds. I keep the publisher's selected translator, C compiler and arguments. My default `-O1`, shadow execution, 1,800-second CLI build budget and separate 120-second corpus budget remain unchanged.

I record each actual subprocess argument vector, executable hash, process identifiers, elapsed tool time and exit status. Before execution, I retain the generated NVM and direct C-compiler file arguments, including the linked runtime object. I do not discover transitive headers or libraries selected through linker options. After execution, I retain the generated C or native output bytes and check the original inputs and tool hashes again. The final CLI artifact contains these copies; the early metadata artifact contains their records. An interrupted observation can retain an incomplete record. I do not treat it as a completed tool call.

My observer adds Python startup, hashing and copy overhead. `tool_elapsed_seconds` covers the subprocess launch and wait; `observer_elapsed_seconds` also includes the measured input/output custody work. The outer compile duration includes observation overhead. I do not use that outer duration as an uninstrumented baseline, and I leave time outside the observed tool calls unattributed. These measurements alone do not establish the full native lifecycle or satisfy the original corpus deadline.

I test the observer with a real C compiler: one native execution, one original compiler refusal, argument/configuration preservation and interruption of a test-owned real preprocessor waiting on stdin. The interrupted record must stay incomplete with its actual tool PID and no invented exit status. The translator setting in that configuration-only unit is not a translator qualification. Fresh audit execution must observe both actual publisher tools and pass the existing CLI contracts before I accept its records.

I also configure an opt-in `NANO_COMPILER_PHASE_RECORDER` executable for my source driver. My driver sends fixed boundary labels through its existing shell host call, quoting both the executable path and label. The recorder writes atomic JSON observations using the same host monotonic clock as my publisher wrappers. I mark imports, lexing/parsing, checked emission, selected shadow assembly/execution, product assembly, native publication and the driver return. These boundaries include recorder launch overhead. A failed recorder returns its actual shell status; it does not change the compiler's acceptance result, and my observing CLI test requires the complete ordered sequence. I retain the outer compiler start and return on that same monotonic clock, so I can measure the interval after the final driver marker separately from summary and log-writing overhead. I add no clock or profiling import to the native host ABI.

My focused source controls execute the helper with recording disabled, a recorder path containing spaces and an apostrophe, a literal phase containing shell metacharacters, and a real recorder refusal. The default empty recorder setting launches no observer. These controls qualify the marker helper; only a fresh compiler run can qualify the driver placements.
