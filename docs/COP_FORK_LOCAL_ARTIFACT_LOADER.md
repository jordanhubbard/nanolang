## My concrete lock audit and proposed preparation boundary

I have no enforced caller serialization today. `vm_ffi_cop_start` forks directly. My daemon starts concurrent client threads, and my callback dispatch starts native workers. My loader write lock covers init, open, shutdown and retained-image mutation; its read lock covers find, symbol resolution, string cleanup lookup and array ABI lookup. `ffi_loader_is_initialized` currently reads without locking. `ffi_loader_get_modules` exposes borrowed storage, and interpreter consumers update `user_data` or dispose it outside the loader lock. I cannot claim these borrowed references are generally safe against concurrent open/shutdown.

I must not take the writer lock before fork and unlock, destroy or overwrite that inherited held lock in the child. POSIX specifies undefined behavior for child operations on inherited held process-private locks. It also restricts a multithreaded fork child to async-signal-safe operations until exec; my existing inline COP worker already exceeds that general guarantee. A loader-only repair must state this remaining boundary, not claim that registry quiescence makes arbitrary provider threads or libc state fork-safe. Primary contract: [POSIX fork](https://pubs.opengroup.org/onlinepubs/9799919799/functions/fork.html) and [read-write lock lifetime](https://pubs.opengroup.org/onlinepubs/9699919799.orig/functions/pthread_rwlock_destroy.html).

For the loader lock alone I propose a lock-free admission word with a closed bit and bounded active-operation count. Every actual registry-lock entrant first acquires admission; it retains admission until after unlocking, including error paths. Thus active operations include lock waiters. Parent preparation makes one compare/exchange from zero to closed; a busy registry causes preparation to fail before fork rather than waiting indefinitely. The parent holds no pthread lock at fork, and no new registry operation may acquire one while admission is closed. Ordinary concurrent entrants wait for the short preparation window to reopen rather than converting temporary contention into a cached missing-symbol result. The word must be proven lock-free on each supported target; an implementation that needs a hidden atomic-library mutex cannot supply this protocol.

The preparation token records the parent PID and a single outstanding transition. Pipe/mailbox setup precedes preparation. The actual fork call immediately follows successful preparation. Fork failure and the parent-success branch reopen admission before other work. Only the changed-PID child with this exact prepared state may adopt the inherited unlocked loader, establish its process-local owner, then reopen admission. Same-PID adoption, an unprepared child and a stale descendant transition refuse without touching an inherited potentially held lock. A later descendant needs its own successful preparation. Adopted shutdown and reinitialization keep child-local mode and never register the parent's SDK callback or alter `sdk_cache_owner`.

I will include the previously unlocked initialized-state read in the guarded API audit. Raw borrowed registry/module pointers keep their existing explicit caller-lifetime restriction; the COP VM uses find only as a presence test and does not mutate interpreter `user_data`. This protocol covers loader registry operations, not a foreign call already executing after symbol resolution, arbitrary direct dlopen users, or provider-private locks. Whether the broader inline COP path must become exec-based remains a separate design decision before claiming multithreaded isolation support.

Before production edits I require review of this boundary. Additive controls must hold a real reader and a real writer from another thread and observe bounded preparation refusal, then successful preparation after release. They must exercise parent fork failure cleanup, concurrent admission reopening, same-PID refusal, changed-PID adoption, unprepared and prepared descendants, exact inherited and newly opened artifacts, and adopted shutdown/reinit. The original SDK callback probe and the actual unresolved `--isolate-ffi` program remain mandatory; cached descriptor tests cannot replace either.
