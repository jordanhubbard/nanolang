# My COP fork-local artifact loader

My reviewed780 gate passes fresh ordinary setup, exact artifact contracts, the retained zero-argument case and new in-process borrowed0/1/2 calls on both hosts. The first isolated call then refuses its selected absolute artifact symbol. Both terminals are retained; no sanitizer phase or later control executes.

The source cause is independent of string ABI: `ffi_loader_init` and `ffi_loader_open` register an SDK shutdown callback before even checking an inherited initialized registry or module handle. `nano_native_register_loader_shutdown` deliberately rejects the parent's callback after fork. Its public contract and `native_sdk_probe.c` explicitly test this refusal. Removing that check or adopting the parent's SDK cleanup owner would violate reviewed behavior.

Before implementation I propose an explicit loader-only transition for the actual COP fork child. The loader records the PID of its successful ordinary registration. A child whose PID differs from that recorded owner may explicitly retain its inherited, address-space-local registry and handles as a child-local loader; it does not register an SDK cleanup callback or change SDK cache ownership. The forked COP calls this transition before normal FFI initialization and performs its existing explicit loader shutdown before exit. Parent registration, conflicting/null callback refusals and inherited SDK registration refusal remain unchanged. A fresh child without an inherited loader follows ordinary registration, including existing conflicts. No provider call is moved into the parent.

This transition needs a precise process-state contract: accept only a real changed PID with existing loader ownership, reject accidental same-process adoption, and require another explicit transition for a later descendant. Once adopted, both inherited exact handles and newly opened child-local artifacts must work; shutdown/reinitialization remain child-local. Filesystem ownership stays with the original `sdk_cache_owner`, and the child's transition cannot remove the parent's private work. I do not claim to repair unrelated multithreaded fork/loader-lock behavior; existing caller serialization remains required and must be reviewed before implementation.

Required controls preserve the original SDK callback probe, verify parent private-work and loader identity after child exit, exercise both inherited and previously unopened artifact paths in the child, and prove exact owner-specific symbols and serialized borrowed snapshots. The actual780 controls must then pass without changing assertions, removing isolation, or suppressing diagnostics. Root/SDK-owner review precedes source changes and execution.
