## My actual entrypoints and the gap

`vm_init` accepts a borrowed mutable NvmModule. `vm_execute`, `vm_call_function`,
`vm_invoke` and `vm_invoke_callable` receive no File host grant. The VM's
`vm_module_ownership_required/supported` reject `nvm_service_execution_pending`
before owned-array or mixed selection. `nvm_verify`, function/linked/profile
verifiers and `nvm2c_emit` likewise reject File claims. `nano_vm` currently loads
an NvmModule and calls ordinary nvm_verify before vm_init/execute. Wrapper
publication checks both supplied module and actual embedded bytes.

I do not remove those guard calls or teach the claim detector that a grant exists.
The detector also recognizes malformed partial metadata and bare/truncated File
instructions; it must remain independent of successful validation. Ordinary
module-based APIs cannot recover the original required-feature envelope from a
mutable module or caller readiness flag.

I add explicit service-aware byte entrypoints to the supported public VM/native
package only after the matched conjunction qualifies. The default APIs retain
refusal. This is a joint guarded branch, not an admission-only change to the old
verifier followed later by handlers. An ordinary program retains its existing
route; a File request with no explicit host grant remains an error.

## My proposed concrete host surface

Production review will fix the public header placement and exact ABI version.
The initial proposed C types and names are:

- Opaque `NvmFileHostGrant`, created by
  `nvm_file_host_grant_create_temporary_files(NvmFileHostGrant **out)` and destroyed
  by `nvm_file_host_grant_destroy(NvmFileHostGrant **inout)`. Creation is the host's
  explicit choice to permit exactly catalog1's five temporary-file methods. It
  does not open a stream. `nvm_file_host_grant_revoke(NvmFileHostGrant *grant)`
  disables a still-live object without freeing it; later execution returns STATE.
  Revocation and destruction both refuse BUSY while public execution is active.
  There is no raw struct constructor or grant wire codec.
- `NvmFileScalar { uint8_t tag; int64_t value; }`, accepting only canonical INT or
  BOOL output. No File, Result, context, capability or nominal handle escapes.
- `nvm_file_execute_bytes(grant, const uint8_t *bytes, size_t size,
  NvmFileScalar *out)` returns the existing `NvmFileRuntimeReport` including first
  site/core status and full secondary cleanup report. `out` is required and
  disjoint; every failure preserves it. It executes the selected hosted entry,
  not an arbitrary caller function index or a persistent VmState activation.
- `nvm2c_emit_file_bytes(const uint8_t *bytes, size_t size,
  const char *entry_identifier, char **out, char *diagnostic,
  size_t diagnostic_size)` performs nonexecuting exact File
  verification and stages generated native output atomically. Emission confers
  no host authority. The generated callable takes a live `NvmFileHostGrant *`
  and `NvmFileScalar *`, returns the same report, and executes actual generated
  functions/labels through the qualified NATIVE arena. It cannot call the VM
  interpreter as an implementation substitute.

The emitter requires an explicit, NUL-terminated `entry_identifier` of 1..63
ASCII characters: the first is a letter and the remainder are letters, digits or
underscore. I examine at most64 bytes and refuse NULL, empty, overlong or invalid
identifiers before publishing output. I do not normalize, truncate or hash names.
The sole program-specific exported symbol is
`nvm_file_program_<entry_identifier>`, with the grant/scalar/report signature above.
Generated byte arrays, facts and helper functions have internal linkage; no
program-specific mutable runtime or gate is emitted. Two programs with distinct
identifiers can link into one process with one owning runtime. The caller must
choose distinct identifiers within that link unit; duplicate identifiers produce
a normal duplicate-definition link error, never weak-symbol replacement. The
emitter returns INVALID and preserves `out` for invalid identifiers. Its diagnostic
buffer retains the separately documented diagnostic-output contract.

These are proposed new opt-in interfaces, not claims that they exist today.
Grant creation/destruction returns explicit OK, MEMORY, INVALID or BUSY status;
exact status enum/header reuse is reviewed before implementation. Public grants
are host policy objects, not security against arbitrary native C memory forgery.
The bytecode/source cannot construct or supply one. A valid grant pointer follows
normal C lifetime rules; dangling pointers after destruction are outside the API.

The grant's policy/catalog/runtime ABI fields are immutable; its live/revoked
state changes only under the runtime gate. It records exactly the temporary
service policy. It grants neither arbitrary paths nor generic FFI, COP, dlsym,
Socket or GPU access. Every invocation explicitly supplies its grant; it creates
one fresh File-values identity and never caches authority on VmState/NvmModule,
a global allow-files boolean, imported type spelling or a prior query result.
A host may reuse a live grant for separate invocations; no live owner crosses them.

## My serialized host boundary is real

The qualified private query/core APIs require external serialization and are not
thread-safe. A public wrapper must not replace that requirement with an ordinary
unsynchronized busy field. I propose one runtime-owned C11 atomic_flag gate over
public File grant lifecycle and the complete preparation/begin/execute/cleanup
interval, shared by both VM and generated-native entrypoints. A contending or
synchronously reentrant call returns BUSY, acquired=false, before touching a
service context or output; it does not wait, finish or dispose the active call.

I define the gate and its operations in the proposed owning runtime translation
unit `src/nanoisa/file_host_grant.c`, compiled as C11. Its explicit object recipe retains the selected `CC`, ordinary
`CPPFLAGS`/`CFLAGS`, warning and instrumentation flags, then appends `-std=c11` so
an inherited `-std=c99` cannot select the wrong language mode. I do not change the
global C99 policy. Only this owning unit includes `<stdatomic.h>` and contains
`atomic_flag`; public and generated-code headers expose opaque grants and ordinary
C function declarations, with no atomic object layout. Generated program units
remain C99-compatible. Every provider path that builds this owning unit must use
the same explicit C11 rule; qualification inspects actual compile commands and
links two separately generated units against exactly one runtime object/library.

All such public entries link the same owning runtime instance and gate. Separate
copies of runtime objects may not exchange grants. Exact linkage/ABI agreement
and multiple generated translation units are qualification controls, not assumed
from symbol names. Direct private-core users still owe their documented external
serialization; the public gate does not make unrelated unsynchronized private
calls safe. Caller-owned grant/output pointer storage must not race destruction
or writes; grant destroy refuses while any public File invocation is active.
Nonexecuting public byte verification/emission also takes the shared gate for
its private query interval, without requiring or creating a host execution grant.
I add no concurrent callbacks, fork inheritance, asynchronous ownership or cross-
process grant transport in this slice. Those cannot obtain an accidental route.

## My fresh verification and matched-handler conjunction

Before any temp acquisition or dynamic-loader attempt I require all of:

1. Non-NULL valid live host grant, supported exact catalog/runtime ABI and explicit
   temporary-service policy. Missing grant returns INVALID, revoked live grant
   STATE, incompatible catalog/ABI UNRESOLVED, and gate contention BUSY, all with
   acquired=false before plan allocation. A freed pointer is not a revoked grant.
2. Actual bounded serialized-v2 envelope with required bits1/9, exact version2
   nominal payload, imports/type maps, flags and cross-section validation. Version1,
   malformed partial claims and forged/mismatched catalog bindings stay refused.
3. The same fresh immutable hosted plan, exact declarations, complete body/CFG
   analysis and all-callee checking used by qualified private targets. No caller
   certificate, mutable module, linked alternate body or cached readiness bypass.
4. Coverage of every decoded opcode, including unused/unreachable code; every
   reachable obligation's exact kind/site/target/rights and known masks must match
   the selected target's actual handlers. Original masks remain hosted/body facts,
   not a fabricated field of NvmFileRuntimeReport. Binding/invocation/liveness/
   rights/borrow/byte/result/cleanup checks execute where required; query success
   alone does not discharge them.
5. Correct VM or NATIVE storage recurrence, actual owning sizeof/cap accounting,
   checked limits and fully allocated roots/staging before begin. The native
   generated ABI/fact agreement remains required at every invocation.

A shared public preparation helper may factor these existing private facts, but
it must not recurse through nvm_verify or broaden shared ownership/union authority.
No new ordinary STRUCT/UNION/OPAQUE interpretation substitutes for catalog identity.
Public diagnostics may describe a verified File profile, but that result is
nontransferable information: execution always repeats the same conjunction with
its own grant and fresh input. No proof object supplied by a caller grants access.

The first public module still has no globals, captures, links, callbacks or generic
foreign imports. Its selected entry has zero arguments and one exact INT/BOOL
result. The first table-order `__init__`, when present, has zero arguments and
zero VOID results. Other named initializers are checked bodies but not implicitly
run. Scalar/owner initializer results remain refused. This grants no generic
public function invocation or owner export API.

## My startup, cleanup and publication

Grant admission creates no stream. After all storage and handler checks succeed,
one invocation owns initializer then entry. Actual initializer RET must close/drop
owners, end originating borrows and pass the cleanup snapshot before entry starts.
A handled close Error can still block entry through the retained cleanup report.
All public incoming owners, owned outputs, captured/globally stored handles,
callbacks and serialized live owners remain refused. Internal helpers may move
File/OpenResult and return them through qualified rooted CALL/RET staging.

The same qualified cores enforce byte0..255 before narrowing, direction changes,
rights/generations/epochs, exact Result fields and close-consumed-on-error. Every
partial argument/return/service result remains rooted until transfer succeeds.
On the first execution error I stop handlers, preserve its site/status, clear
formal aliases before origin borrows, drain all actual owners, then dispose the
core. Secondary cleanup failures remain visible. I release the public gate only
after terminal cleanup. Success publishes the two-field scalar after everything
is clean; a failed close cannot publish a successful earlier computation.

## My preparatory grant checkpoint25bb

Before source changes I fix ABI1 in `src/nanoisa/file_host_grant.h`. My distinct
`NvmFileHostStatus` values are OK=0, INVALID=1, MEMORY=2, STATE=3,
UNRESOLVED=4 and BUSY=5. This is a grant/preparation status, not a fabricated
runtime cleanup report. Lifecycle returns this enum. Catalog1/policy1 and ABI1
are immutable fields owned by the opaque heap object. Revocation is idempotent
and only changes its live flag. Destroying a NULL object through a non-NULL
pointer is idempotent; a NULL pointer-to-pointer is INVALID. Creation publishes
only on success and never reads the old output pointer. Live output storage must
not alias another live grant; replacing a live pointer would lose caller ownership.

A single owning `file_host_grant.c` has one statically initialized atomic_flag.
Every lifecycle method tries it before inspecting caller pointers, so contention
has BUSY precedence, including otherwise-invalid inputs, and never allocates or
modifies them. Uncontended malformed arguments return INVALID. I free under the
gate and null the caller pointer before release. A caller still owns all valid
pointer lifetimes and must not race destruction with storage reuse or dereference;
this gate is not a safe dereference protocol for dangling pointers.

`file_host_grant_internal.h` exposes trusted-adapter-only balanced operations:
`nvm_file_host_enter_query()` and `nvm_file_host_enter(grant, abi, catalog)` return
OK while retaining the gate, and `nvm_file_host_leave()` releases it. Every
non-OK entry releases any lock it acquired; BUSY never releases another entry.
The successful calling thread must leave exactly once after full cleanup. These
internal functions are not a caller-supplied execution certificate or callbacks,
and a non-owner or repeated leave violates their C API precondition. Native
memory can already call private cores; this is not an adversarial C sandbox.
Successful grant entry checks its owning runtime identity, live state, exact ABI,
catalog and policy. Missing grant is INVALID, revoked is STATE, incompatible
identity/ABI/catalog/policy is UNRESOLVED. No plan or host stream is allocated.

Only an explicit `file-host-grant` Make target builds this object initially;
I do not add it to default NanoISA/module/wrapper provider lists before matched
public integration. Its recipe uses CPPFLAGS/CFLAGS and a final `-std=c11`.
Fixtures compile two ordinary C99 consumers against the same object, plus a
separate instrumented build of that same source for allocation failure and
otherwise inaccessible metadata mismatch controls. Pthread synchronization
holds the lock deterministically for contention assertions; no timing retry is
used to obtain BUSY. These consumers model future adapters; they are not emitted
programs and do not qualify the later generated-name/package requirement.
There is no service handler or host access in this component. Missing-grant
execution refusal/loader attempt tests remain the later joint-routing obligation.
