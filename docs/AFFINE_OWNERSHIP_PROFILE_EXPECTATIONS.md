## My observed conflation

`tests/test_affine_contract_boundaries.py` constructs each exact source as its
shared `PREFIX`, the case declaration and the same scalar `main`. Its
`check_case` helper currently gives `nanoc_c`, `nanoc_stage1` and
`nanoc_stage2 --target c` one shared `accepted` result. That result therefore
means two different things at once:

1. my parser, typechecker and affine checker accept or reject the complete
   source; and
2. the selected explicit C backend can publish that checked program.

These are not the same authority. My C reference driver completes
`type_check` and shadow checking before `c_backend_emit`. The backend has an
independent reviewed profile: it refuses first-class callable values and
indirect calls, and it admits only scalar payloads in exact local union
results. `indirect_result_owner` and `union_return` pass the ownership rule but
cross those two later publication boundaries.

The cases are canonical release-gate inputs. `make test-quick` invokes
`test-affine-selfhost`, whose shell runner includes
`tests.test_affine_contract_boundaries`. Their appearance in the earlier
focused imported suite was accidental; their membership in the ordinary gate
is not.

## My four explicit authorities

### 1. C frontend checking

I add one test-only C runner linked from the same parser, typechecker,
environment, module and runtime objects as `nanoc_c`. It reads the exact case
file and follows the checked frontend sequence already used by `src/main.c`:

1. tokenize and parse the complete source;
2. create the environment and module list;
3. process imports;
4. call `type_check`; and
5. call `type_check_shadow_scope` when checking succeeds.

The runner stops there. It never calls `c_backend_emit`, a transpiler, a native
compiler or an executable. It adds no production command-line option and
publishes no output artifact. Its exit status must match the unchanged
semantic expectation for all36 cases. This is the actual C frontend authority;
successful or failed C publication is not a substitute for it.

The exact corpus has no imports or shadows, but the runner retains the real
driver sequence so that the test-only boundary does not become a second
simplified typechecker contract. It releases the AST, tokens, environment,
module list and module cache on every path. A parse failure cannot count as a
typecheck refusal.

### 2. C-seed public C publication

I retain `bin/nanoc_c <source> --target c -o <output>` as a separate backend
contract. Each invocation begins with a known prior output artifact.

The existing public-C-supported positive cases must still publish and replace
that artifact. Existing semantic negatives must still refuse during checking
and preserve it. The two reviewed profile exceptions instead require these
exact backend outcomes after positive frontend checking:

- `indirect_result_owner` refuses with `I do not provide first-class callable
  values or indirect calls in this C profile.`
- `union_return` refuses with `I require scalar C union result payloads.`

Both refusals preserve the prior output. Neither may be reported as an
ownership/typecheck rejection, and neither authorizes a new representation or
calling convention. A future public-C ABI proposal would be separate work with
its own contract and qualification.

### 3. Self-hosted explicit C publication

I keep `nanoc_stage1` and `nanoc_stage2 --target c` separate from the C-seed
public backend. Their current original-case expectations, including the two
semantic positives, remain unchanged. A failure on either route is its own
self-hosted transpiler defect; it cannot be hidden by the public-C refusal
mapping or used to weaken the source expectation.

### 4. Canonical executable selection

I retain `tests/test_checked_owner_selection.py` unchanged as the executable
authority until the route-specific harness is reviewed. Its test driver is
compiled by `nanoc_c`, `nanoc_stage1` and `nanoc_stage2`; each resulting driver
parses and typechecks the whole original source before calling program-mode
NanoISA lowering. Accepted assembly remains identical across the three
producers, excludes the unselected foreign declaration, assembles, verifies
and executes through VM and strict native translation.

The same14 positives continue through the actual Stage1 and Stage2
`--emit-nvm` CLI and VM/native execution. Program selection happens only after
full checking. Raw `nanoisa_emit_parser_nasm` remains the all-definition API
and retains its existing refusal; its behavior is not evidence against
program-mode selection.

## My harness shape

I keep one semantic case record and derive route expectations without changing
its source or `accepted` field:

- `semantic_expected` is the original `accepted` value;
- `c_frontend_expected` equals `semantic_expected` for every case;
- `public_c_expected` equals `semantic_expected` except for the two named,
  exactly diagnosed profile refusals;
- `selfhost_c_expected` retains the original expectation; and
- `canonical_expected` equals `semantic_expected` and keeps the existing
  selection/execution assertions.

The public-C exception table is closed and name-specific. An unknown case
cannot inherit a refusal, and diagnostic substring matching cannot turn a
typecheck error into a backend-profile pass. The harness asserts the36-case,
14-positive and two-profile-exception counts before invoking any compiler.
