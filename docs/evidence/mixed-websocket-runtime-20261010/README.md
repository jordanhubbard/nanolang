# My mixed WebSocket runtime evidence

I connect mixed File/TCP/WebSocket values to checked VM and generated native
execution. Each WebSocket instance receives a copied explicit policy before
core creation. My public entries authorize the entire checked table before
installing policies; File/TCP grants and the older single-input runtime API
remain separate from the new ordered-argument adapter.

I select catalog-specific types, owner/borrow identities, nine-field errors and
string-bearing Message/ReceiveResult payloads. I skip exactly the unused fifth
WebSocket import while retaining active-import checks. Native agreement records
both present members and absent slots. I reserve a shared 32 MiB WebSocket core
budget only for tables that declare it, within my 64 MiB total runtime limit.

My LLVM ASan/UBSan/leak-checked runtime suite passes six non-network methods.
The seventh method, required live-peer execution, fails at listener bind with
EPERM. I retain that failure; I do not skip it or call the target green.

The passing methods cover:

- 24 direct/indirect, loop-containing and nominal-permutation graphs over one
  WebSocket, File/TCP/WebSocket/WebSocket and five repeated WebSockets. I compare
  actual VM reports with separately compiled generated native programs.
- Instance-specific copied resolver paths, lookup bits and deadline ceilings;
  denied/wrong-catalog/revoked grants refuse before acquiring cores.
- Embedded-NUL received messages different from the sent literal. My receive
  path must allocate a fresh runtime string before later equality checks.
- Send and receive errors, cleanup failures, and instruction limits 0, 3, 7,
  16, 28 and 40 with exact VM/native report and output-preservation parity.
- All 15 runtime/core/string allocation-failure prefixes, including cleanup of
  partial construction and live connections, with leak checking enabled.
- Negative close deadlines consuming every connection, real transport
  invalid-URL results, and generated C99 consumers using only relocated
  installed headers/archive for the mixed and five-WebSocket graphs.

My strict live graphs prepare and compile, including the five-instance graph.
Initially its main function contained 274 instructions, exceeding the existing
256-instruction limit. I move send assertions into its existing checked helper
and use region-end borrow cleanup, retaining every success assertion. Main now
contains 254 instructions; helpers contain at most nine. The live test requires
all connection/send/receive/close results to succeed and counts all 16 peer
messages across VM/native runs. It remains unqualified because bind is refused.

My strict GCC C99 compile first rejects generated `stack_count < 0` checks for
zero-argument File operations. I retain that failure, emit stack-size checks
only for nonzero argument counts, and initialize argument storage. A separate
portability method passes with the corrected emitter: it compiles and executes
the mixed generated program using GCC 16, ordinary C99 and only the relocated
archive, and matches the sanitized VM report. This is ordinary GCC execution,
not a GCC leak-check pass. The earlier GCC LeakSanitizer exit hang stays open.
My mixed runtime source also compiles as strict GCC C11 without instrumentation.

My five mixed flow/policy methods, five standalone WebSocket product-driver
methods and repeated File/TCP product permission method pass. The flow suite
checks missing/invalid/duplicate runtime policies and retains the malformed
module and cross-instance refusals. The first runtime compile's missing catalog
include is corrected explicitly and its failed build is retained.

I still refuse mixed WebSocket in product-policy parsing pending paired source
integration. Live-network qualification, exact-candidate Linux/Darwin gates and
the historical full native text-reader incident remain open. I do not close #990
or claim that these runtime results complete release 5.1.
