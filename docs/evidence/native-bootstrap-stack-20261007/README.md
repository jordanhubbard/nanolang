# My native-bootstrap stack and Darwin cache checkpoint

My translated C-seed compiler compiles hello but overflows Darwin’s 8 MiB stack when compiling the full compiler source. The first crash is in `parse_primary`; ASan independently reports stack overflow through parser recursion. I retain the input module compressed, the focused diagnostic and reduced crash records. That diagnostic ASan run disabled leak reporting solely to locate the fatal signal; it is not leak qualification. My focused regression executions below retain leak detection.

My repeated-record-call regression measures a 440,672-byte frame before correction. I pass internal record arguments by address, copy them into invocation-owned locals and write record results into caller-owned slots. My separate tail-reset regression measures 422,752 bytes before correction; I clear heap record locals in place and retain parallel argument snapshots. With both corrections, Clang at `-O0` measures `parse_primary` at 55,376 bytes and `parse_expression_recursive` at 6,960 bytes. The first pointer-only correction still overflowed; I retain its crash as well.

Thirteen focused tests pass, including recursive record values, tail swaps, frame bounds, ASan/UBSan with leak detection, allocation failures and all nine methods whose external C harnesses directly invoke the internal record ABI. The earlier broad run passed 2,431 structured-C checks, then failed 87 harness compilations because those harnesses still used the former by-value ABI. I change the calls, not their payload, tag, refusal or allocation assertions. My final full product rerun now also requires the translated native compiler to emit a module from its entire compiler source. That rerun remains pending.

My clean VM bootstrap at `5e85cbac2` emits Stage 1 in 464.391 seconds and verifies it, then fails the immutable-host-closure assertion: `compiler_support` has a new generation and hash. Stage 2 does not run. A direct host-artifact probe reports missing linker evidence on repeated builds. My Darwin response-file admission mistakes literal `@` in Homebrew’s `openssl@3` path for response syntax. I distinguish literal path characters from actual token-leading or forwarded response controls. The new reuse/invalidation fixture fails before correction; it and three adjacent literal-path, response-capture and linker-mutation tests pass afterward. I have not weakened the exact host-closure comparison.

I also remove the module loader’s transitive dependency on the C emitter for a filename-suffix check. Its replacement helper and shadows pass compiler bytecode emission and verification. The product driver still retains the legacy emitter; this checkpoint is not the NanoISA-only cutover or a 5.1 release.
