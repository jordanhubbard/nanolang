## My proposed launch and transport contract

I propose replacing the production inline fork worker for all COP callers, rather than guessing whether a process currently has other threads. The parent uses `posix_spawn` with an absolute, verified sibling `nano_cop` executable from its resolved runtime image or the existing validated SDK root. I do not search PATH, execute a shell, or fall back to a parent-side foreign call. `scripts/native_sdk.py` already includes nano_cop among public installed executables; focused Make prerequisites and standalone API fixtures must explicitly include the worker instead of relying on an unrelated earlier build.

I retain both current transports. A private, immediately unlinked shared-memory object replaces the anonymous inherited mailbox; the spawned worker maps its descriptor at any address. The existing signal pair and data pair remain per-worker. Parent-side descriptors are close-on-exec, duplicated above reserved child descriptor numbers before spawn actions to avoid dup2 alias collisions. On Linux the actual libc header exposes `posix_spawn_file_actions_addclosefrom_np`; on Darwin the actual SDK exposes `POSIX_SPAWN_CLOEXEC_DEFAULT` and explicit inheritance actions. I require closed-by-default descriptor inheritance with only the mailbox, protocol endpoints and intentional standard streams surviving. I will not assume the GNU action exists on Darwin: [GNU's portability inventory](https://www.gnu.org/software/gnulib/manual/html_node/posix_005fspawn_005ffile_005factions_005faddclosefrom_005fnp.html) explicitly distinguishes those platforms. Every action, allocation, mapping, spawn and handshake error must close only owned descriptors, unmap owned storage and reap only its worker.

Initialization transfers a bounded immutable serialized module snapshot before READY. The existing public `nanoisa_save_bytes`/`nanoisa_load_bytes` v2 route is the candidate transport, not the older internal `nvm_serialize` v1 writer. The worker must validate container and import contracts, retain exact artifact kinds/paths/owners, argument/result tags and callback policies, and refuse capture/service/pending callback execution as today. Cached runtime function pointers are deliberately absent from serialization and must resolve independently. My current standalone `cop_main` already receives a module but preloads via the logical-name helper; it must use actual import-kind-aware loading and share one initialization implementation with the mailbox worker. Import-only modules built by the public C FFI fixtures also need valid metadata transfer; requiring unrelated executable entry code would silently narrow that API.

I preserve current mailbox sizes, batch cap, ordering, large pipe spill, owned string/array snapshots and the same persistent worker for all calls from a VM. Existing single-call pipe fallback already supports the same reply publication, but replacing mailbox batching wholesale with repeated pipe calls would change the requested performance/transport contract. The startup deadline remains five seconds for the complete initialization exchange; existing call deadlines remain unchanged. Missing/incompatible workers, truncated or excessive initialization, unexpected READY, broken channels and timeout must fail closed. Crash/restart retains the existing per-VM restart boundary.

Three semantic boundaries need explicit closure before implementation approval. First, exec starts providers with their own initial state; it cannot reproduce arbitrary parent-side native global mutations previously copied by fork. Existing isolated calls must retain within-worker state, and tests must establish whether any supported caller promises a parent-provider snapshot. Second, opaque replies currently carry pointer-sized payloads: a value created in the worker can return to that same worker, but parent-created pointers or stale pointers after restart cannot gain authority merely through serialization. I must inventory actual supported opaque producers/consumers and preserve or enforce their owner lifetime. Third, embedded/custom VM binaries need the same explicit runtime-worker discovery contract as installed and checkout CLIs; sibling discovery alone does not cover fixtures built outside bin.

I require additive actual concurrent daemon-client tests while another thread owns a loader reader/writer and while a callback worker is active; no inherited lock should affect an exec worker. Descriptor inheritance, wrong/absent worker refusal, malformed module initialization, import-only C API modules, first unresolved exact artifact calls, native state persistence, mailbox batches, large strings/arrays, opaque owner/restart behavior, SDK/cache survival and worker cleanup must all be reviewed and qualified on both hosts with instrumentation. This proposal is source-only; the unresolved semantic boundaries are release obligations, not acceptance exceptions.

## My proposed generation and slot contract

I propose a distinct tag-specific opaque owner field using NanoValue's existing owner padding, preserving its16-byte layout and callable owner semantics. Owner zero denotes existing process-local raw pointer values and canonical null. A nonzero owner is a monotonic, process-unique COP generation assigned when a VM starts a worker; exhaustion refuses a launch, never wraps or reuses an owner. Each launch also records its parent PID, so copied VM state after an unrelated fork cannot authorize another process's worker.

An isolated opaque value contains that owner plus a nonzero64-bit slot. The worker alone stores slot-to-native-pointer rows and reverse identity. Repeated returns of the same pointer from the same live worker reuse a slot, preserving identity. Null is canonical zero and needs no table row. Slot allocation/growth is checked before publishing a result; allocation failure cannot publish an invented token. Table teardown frees only table metadata, not borrowed provider objects. Provider-specific disposal APIs retain their original ownership contract; this table does not promise to detect a native provider that frees and reuses an address within one generation.

Before encoding, the parent accepts only canonical null or an issued slot belonging to that VM's current live generation. Arbitrary nonzero integers, local raw pointers, other VMs' tokens and old generations refuse before FFI. The wire opaque payload remains a slot interpreted only within that worker channel. Before dispatch, the worker validates declared arity/type and resolves every slot through its own table; zero is the only integer null spelling admitted. After dispatch, opaque arguments/results are mapped back to slots before the existing scalar/envelope codec. The parent installs its generation only after the complete reply, slot publication and array mutation checks succeed. No raw address or supplied owner is trusted from serialized input.

Tokens must also refuse at in-process native argument and callback-result boundaries: a value cannot become a raw pointer simply because a caller changes isolation mode. Full value copies keep the owner. Equality distinguishes owners; same-worker aliases compare equal; null remains equal to the language's integer zero. Ordinary opaque ordering stays outside the accepted language contract, but internal generic comparison must not collapse distinct isolated identities. Validity examines the full slot and live generation, not the current low32-bit field. Native in-process pointer behavior remains separate.

Required controls create two simultaneous workers, return the same native pointer repeatedly, copy tokens through existing boxed carriers, pass a token back successfully to its owner, and refuse it in the other worker, after restart, from an in-process parent pointer and through a local callback return. They cover null, slot/generation exhaustion, allocation refusal, unchanged result/argument publication, full-width slots, malformed/unissued wire slots, all three worker transports and persistent provider state. No new opaque-array acceptance is proposed. This is a source-only contract awaiting review and implementation; the exec-worker task cannot close without these ownership obligations.

The construction audit must initialize the tag-specific owner at every opaque producer. Existing production marshal results, callback values and null opcodes already zero-initialize their values; low-level stateless codec fixtures may leave unused padding unspecified and must not become ownership validators. Any new public local-opaque constructor must initialize the whole value, and C API documentation must require a fully initialized opaque value rather than reading unspecified old padding. Boxed arrays preserve whole NanoValues; only INT/FLOAT/BOOL/U8 arrays use packed storage. Hash-map lookup uses `val_equal` (its current default hash collides but does not establish equality), so owner-aware equality must remain consistent through those carriers.

## My pre-call capacity refinement

Before any foreign call with a declared scalar opaque result I reserve one worst-case new worker pointer-table row and bounded reply-publication storage. A batch reserves its complete declared opaque-result upper bound before its first foreign call. A repeated pointer may reuse a row, but capacity checks cannot assume it will. Failure leaves outputs and the provider call count unchanged. The parent keeps explicit issued-slot membership, with worst-case growth reserved before foreign entry. A high-water mark is insufficient: an unpublished worker slot must not become authorized when a later slot is published. Publication into reserved membership storage performs no allocation. Failed-publication then later-success controls must preserve refusal of the earlier unissued slot.

This prevents metadata allocation failure from stranding a newly returned pointer without a worker table entry. It does not invent a provider disposal API: table teardown frees metadata only. Existing mutable array/string reply snapshots can still fail after native side effects; the current protocol cannot roll those side effects back. A result already interned in the worker table remains attributed there even if reply transfer/publication fails. Generic disposal of a provider-owned pointer needs an actual declared disposal contract and is not established by this token table. All allocation failure claims will name this precise boundary.

My actual scalar opaque result capture must occur at `marshal_result`, before `vm_ffi_arrays_commit` can fail. An explicit scoped capture parameter passed through the call implementation is preferable to a global observer: it records the returned native pointer in already reserved worker metadata even when later mutable-argument validation refuses publication. Local callers pass no capture and retain their existing raw-pointer representation.

My token implementation audit also requires declared OPAQUE parameters/results to select existing typed libffi pointer dispatch, even below the general wide-signature threshold. A token is resolved before this boundary; the actual provider pointer is captured immediately after the call, before fallible array publication. My parent reserves a reusable maximum bounded wire reply before any opaque-result call, including mailbox spill.
